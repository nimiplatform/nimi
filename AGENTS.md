## Hard Boundaries
- Repo-wide normative authority lives under `.nimi/spec/**`; retired pre-cutover authority history now lives in Git and must not regain active truth. Admitted app slices may live under `apps/**/spec/**` if they do not create parallel truth. Nimicoding package authority lives in the external `@nimiplatform/nimi-coding` package; this host consumes its retained methodology and deterministic tooling through the guarded package scripts and admitted `.nimi/{config,contracts,methodology}/**` host projections. Host-local truth lives under `.nimi/**`; `.local/**` is legacy local execution/evidence compatibility space; tracked support inputs live under `config/**`; `dev/**` is inactive.
- High-risk authority-bearing work needs preflight before implementation with `Spec Status`, `Authority Owner`, `Work Type`, and `Parallel Truth`.
- `Work Type=alignment` must align to existing authority with no parallel truth. `Work Type=redesign` changes authority/canonical ownership and must not proceed without prior `/.nimi/spec/**` alignment.
- Debug/fix order: `runtime` → `sdks/typescript` → `apps/desktop`/`apps/web`. Reuse `@nimiplatform/kit` first for UI work via `kit/README.md` and `config/platform-nimi-kit-registry.yaml`.
- UI/UX work: read `DESIGN.md` and `kit/DESIGN.md` before changing shared Nimi UI surfaces. Treat them as generated AI/tool-facing projections from `.nimi/spec/canonical/platform/ui-design-system.authority.yaml` + `config/platform-nimi-ui-*.yaml`, not canonical authority. If the projection is missing, stale, or conflicts with the canonical container, update the relevant `config/platform-nimi-ui-*.yaml` tables first and regenerate with `pnpm generate:nimi-design-artifacts`; do not hand-edit generated design artifacts.
- Design artifacts: `kit/design_tokens.json`, `kit/design-projection.json`, and `kit/tailwind-theme.css` are generated interoperability/projection outputs for tooling and audits. They follow Nimi's Tailwind v4 CSS-first stack and must not become runtime truth; runtime Kit CSS still comes from the existing spec-derived UI generation path.
- Fail closed on contract violations. No legacy shims, no pseudo-success, no app-level REST bypass, no provider/model hardcoding.
- Boundary enforcement: Desktop/Web must not import `runtime/internal/**`; SDK must not cross `realm`/`runtime` private boundaries; Runtime must not import `sdks/**` or `apps/**`; no file collisions or forwarding shells outside `index.ts`.
- Workflow ownership: the external AI host exclusively owns task lifecycle, planning, decomposition, subagents, waiting, resumption, and completion state. Nimi-coding must not create, mirror, advance, resume, close, or execute host workflow state. Use only the guarded package scripts declared in `package.json`; direct package bootstrap, projection mutation, and package workflow commands are forbidden.
- Nimi2D Image2: use the standard `@nimiplatform/nimi2d` provider command surface for live image resource generation: `image2-provider-plan`, `image2-provider-run`, `image2-register-output`, `image2-compare-pixels`, `image2-postprocess`, `image2-layer-workflow`, `image2-distribution-report`, and `image2-demo-suite`. On Windows, if PowerShell blocks the `codex.ps1` shim, use `image2-provider-run --codex-bin codex.cmd`. Never use ad hoc session prompts as provider evidence, and never treat provider artifacts as formal admission before atlas, layer-input, Generation Bench, and runtime proof gates pass.

## Execution Priority

- Explicit current user direction and completed phase decisions are fixed execution inputs. Do not reopen them from historical plans, checkpoints, old evidence, filename heuristics, or unrelated validation failures.
- For an authorized implementation or product-gate task, proceed to the real build/install/launch/journey before repo-wide audit or later-gate design. `not_observed` is not `invalid`; no blocker exists until a real path fails or an exact required authority/configuration path is proved absent.
- A lower-level or later-gate mismatch cannot change the selected product topology or block the current gate unless it is a direct prerequisite of that gate.
- Retrieval Defaults and Verification Commands are scoped menus, not mandatory pre-run checklists. User-provided bounded include/exclude and targeted verification scope override them while Hard Boundaries remain in force.
- Do not recursively load `.nimi/local/plan/**`, `.nimi/local/handoffs/**`, or historical evidence for an execution task. An explicitly named current-only snapshot may be read; any other local plan/evidence file is on-demand only after the current failure points there. Do not run broad `git status`/diff merely to understand unrelated dirty work; inspect only affected paths.
- Keep a linear product journey single-agent unless independent concrete subtasks can be completed without changing its direction or gate state.
- For pre-release local product-gate runs, an incomplete Product Control record bound by an earlier wrong-root attempt is bounded machine residue, not a product blocker. When the operator has fixed the intended product root and no passed Gate evidence exists, the canonical Gate 0 command uses `scripts/reset-windows-first-party-product-control.ps1` through `--reset-stale-first-run-control` to clear only the stale fixed-service Product Control/data-root control files, preserve the product-root payload, and rerun the same Gate. Do not add a product reset RPC, migration, compatibility path, profile, or evidence mechanism.
- A stateful product harness must finish every harness-only source, identity, configuration, and contract precondition before its first durable product mutation. After the canonical product owner reports success, an auxiliary projection or evidence-writer failure is a harness defect and must not be relabeled as product failure, trigger automatic product-data cleanup, or force replay of an already completed action; use bounded read-only recovery or an explicit one-time non-product cleanup instead.
- P4 has one active acceptance target: the linear ordinary-Electron product journey `pnpm test:e2e:first-party-product:p4`. Git/worktree snapshots, source-tree hashes, test-file edits, artifact manifests, historical point mappings, auxiliary Runtime readbacks, and evidence completeness are diagnostic only and cannot fail this target. Stop only on the first real build, install, launch, OAuth, product-owner, Nimi Chat, partner UI, or reload failure; fix that failure and rerun the same target.

# Nimi Coding Managed Block

- Product authority lives under `.nimi/spec/**`.
- For canonical authority authoring, read only `.nimi/methodology/authority-authoring.yaml`, the affected authority files or bounded task context, and CLI diagnostics.
- Use `nimicoding authority context <path> <id> --max-units <n> --max-bytes <n> --json` only for the complete declared outgoing interpretation closure; it is not complete task context, and failure never permits guessed or partial context.
- Use `nimicoding authority diff` and `authority impact` with explicit `--max-bytes`; impact reports declared review obligations and does not prove implementation, consumers, or tests are synchronized.
- Under `.nimi/spec/**`, author only closed multi-unit `*.authority.yaml` containers or single-unit `*.authority.md`; historical document formats are unsupported and never inferred.
- Run `nimicoding authority fmt` on each changed file, then `nimicoding authority check` on the complete authority input set.
- Never bypass a failure with inferred or fallback semantics; choose repair values only from product/task authority.
- Keep derived and verification evidence under `.nimi/local/**`; it is never product authority.
