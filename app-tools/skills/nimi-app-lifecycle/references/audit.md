# Adaptation feasibility and cost audit

Use this guide when the user wants to decide whether to adapt an App, assess Nimi capability fit, or obtain a costed implementation plan. The output is decision evidence. A future desire to adapt does not authorize current product/spec edits, init/sync, installation or release. Source retrieval and bounded checks may support the audit; use the user's actual scope and resources. If implementation is explicitly included, continue it after the necessary decisions rather than asking for the same authorization again.

## Establish scope and the existing route

For an unspecified Nimi ecosystem adaptation, assess preserving the core product tasks and connecting them through the formal SDK/Kit App carrier. State this working scope and proceed. Respect an explicit model-only, server or other target. Ask only about a material unresolved choice; do not introduce backend removal or a full rewrite as a default option.

Pin the upstream revision and the Nimi source/package combination available to this audit. Note only local uncommitted changes relevant to a conclusion. Distinguish current source capability from what the selected installed or published packages expose.

Read the target's nearest instructions, package manifests and actual product entry to identify its core tasks. Then establish Nimi's existing public consumption route from the selected lifecycle guidance, SDK public types/support notes, and the implicated Kit Host entry before estimating integration work. Host business services and existing framework adapters are reusable inputs, not discoveries to defer until after a broad platform search. This reading does not require installing a package or initializing the target App.

Trace the App's actual task and AI call paths: required inputs/outputs, tool and structured-output behavior, retrieval and persisted results, cancellation/recovery, and any helper-process or hosting boundaries that the task uses. For each material need, identify whether it is essential to the requested user task, an explicitly selected option, conditional on a provider/backend, or an implementation detail of the old foundation. Use actual consumers, defaults and activation conditions as evidence. Defaults alone do not define importance: an optional feature is required when the user's requested workflow depends on it. Do not turn every reachable code path into mandatory adaptation scope, or silently remove a selected feature to make the assessment easier.

Follow the unresolved dependency into its exact Nimi owner. Start with bounded files and symbols; do not enumerate unrelated Apps, read the whole authority corpus or repeatedly dump broad source slices. Existing adaptation history is useful only when it resolves a specific reuse or failure question. Read direct package manifests before choosing runnable checks.

## Classify fit before proposing work

For each behavior in scope, connect the App consumer and expected result to the Nimi public contract, actual execution/carrier support and applicable conditions. A blocker must name the workflow, option or delivery stage it blocks. Separate preserving a user capability from reproducing an old provider/configuration control; a difference in controls does not by itself establish that Nimi's configuration ownership must expand. Distinguish:

- Existing support and the configuration or documented usage needed to use it.
- An existing-contract implementation defect, or a missing SDK/Kit/native/framework carrier.
- A missing exact Driver/adapter behavior, a contract-local feature/result extension, or an independent new CapabilityContract.
- App-owned business work, deployment prerequisites, and model-content quality.
- An unresolved question whose evidence is not yet sufficient.

Check a proposed public call through its admission, allowed execution mode and dispatch to the required result. A request union or projection branch may still describe a path rejected by the owner. An available alternative mode is usable only if it satisfies the workflow's required interaction and lifetime. Catalog membership, a method name or a previous success alone does not prove the combination; unread code, missing setup or an unrun platform does not prove absence. A code-confirmed missing operation does not require Desktop startup to report.

Use current Nimi authority for semantic ownership and source/tests for actual implementation. For example, distinguish the App's tool loop from Runtime model execution, a framework adapter from a provider Driver, and task data from canonical long-term Memory/Knowledge. Do not preassign every backend subsystem to Runtime or count shared SDK/Kit behavior as new App-specific work.

Estimate residual work after reuse for the stated scope. Keep App integration, shared Nimi changes and environment/acceptance costs distinct. When options materially change effort, separate the viable core journey, selected extensions and conditional coverage increments rather than summing every upstream option into one headline. A full-coverage estimate is useful when clearly labeled; it is not automatically the entry cost or an accepted scope. State the effort basis, assumptions and confidence, using comparable work where available; do not equate human person-weeks with AI-assisted elapsed time. If the basis is weak, give difficulty and decisive uncertainties instead of a precise schedule. A bounded prototype is useful only when its answer could change the decision, not as another mandatory audit gate.

## Use proportionate evidence

Run a bounded check only to resolve an uncertainty that affects the decision. Do not create a reference App, install models, execute the whole product/release journey or run broad suites just to begin an audit. If a real protected call is necessary and within scope, use the supported owner path; otherwise state the dependent limitation and continue the rest of the assessment.

For material conclusions, identify the evidence kind: declared contract, inspected implementation, actual execution, applicable prior evidence, or hypothesis. Cite the relevant revision and code/rule or run where useful. Keep unexecuted paths NOT-VERIFIED and make unknowns local to the affected claim. Existing successful evidence is not erased merely because this auditor did not rerun it.

## Deliver a decision-ready report

Scale detail to the requested audit depth. Lead with whether the App is a good candidate now, conditional on specific extensions, unsuitable under the stated constraints, or awaiting a named decisive fact. Explain the core tasks and architecture needed to understand that conclusion.

Include a requirement-to-Nimi mapping with the consumer, necessity/activation condition, required result, usable route and mode, gap classification, proposed owner/change and evidence. Separate confirmed blockers from assumptions and recommendations, including in interim updates. Tie costs and the implementation sequence to the same scope and actual dependencies; optional platform work need not block an independent core journey. Include stage-specific acceptance and likely reusable platform gains. Compare alternatives only for real unresolved decisions.

Preserve the user's product scope. Do not make a candidate appear feasible by dropping a core workflow, changing an explicitly required deployment or assuming an unsupported model behavior. Do not promise whole-product acceptance from protocol tests. Keep the report in the requested deliverable or existing project notes, not a new approval or evidence system.

## Handoff to implementation

An audit is a revision-scoped assessment, not canonical product authority. The user's confirmed goals, constraints and selected direction persist; report recommendations, inferred gaps and estimates remain evidence-dependent. Authorizing work from an audit does not make every assertion in it true or override current owner contracts.

Before a consequential implementation choice, check the particular assumptions it depends on against the current contract, implementation and confirmed scope. Reuse sufficient evidence where those inputs still match. Revisit a claim when they changed, a contradiction appears, or the original basis was hypothetical or did not cover the decision. Preserve conditions such as a selected optional feature or full-coverage target; neither a broad estimate nor a recommendation turns every listed extension into a prerequisite. Do not restart the whole audit or seek blanket reapproval.

When current evidence disproves a claim, correct the plan and estimate within the authorized scope, explain the changed basis, and clearly supersede that claim in the existing current summary. Ask only if resolving the contradiction would materially change the user's confirmed outcome or scope. Never implement an obsolete or false claim merely because the audit used definitive wording or the user said to proceed with its plan.

Carry these distinctions through task handoffs and context summaries: user decision versus recommendation, observed fact versus hypothesis, and applicable revision/conditions versus broader unknowns. Do not shorten 'possibly missing' to 'missing', 'recommended' to 'required', or 'not run' to 'unsupported'. Link to the evidence instead of repeating a conclusion until it appears authoritative. Implementation continues through [Adapt](adapt.md) and, when needed, [Platform gaps](platform-gaps.md).
