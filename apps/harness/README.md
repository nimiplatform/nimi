# Nimi Harness

Nimi Harness runs a Pi durable conversation in a Desktop-supervised Electron host. Runtime supplies the partner’s configured model. Harness owns the local transcript, tasks and tool approvals.

## Workspace development

Run the following from the Nimi repository root with Node 24, the pnpm version pinned in `package.json`, and the Rust toolchain and native linker for your host. Harness uses the SDK, Kit and App Tools from this workspace.

```sh
pnpm install --frozen-lockfile
pnpm --filter @nimiplatform/harness test
```

The test command builds the workspace SDK and Kit. On macOS and Windows it also compiles the native Kit module used by the file preview test. The test build goes into Cargo’s debug directory.

To run Harness, start Nimi Home with a matching Runtime, sign in and enable Developer Mode. Use `pnpm dev:harness` for first launch. To return to existing App data, run `pnpm dev:harness --list-registrations` and pass the current selector to `pnpm dev:harness --resume <selector>`. Choose the partner’s text model in Nimi Home.

## Native packaging

Build on the target host. Prepare the matching Kit native package for the intended host trust profile. The production builders are `node kit/shell/protected-local-node/scripts/build-darwin-arm64-package.mjs` on Apple Silicon and `node kit/shell/protected-local-node/scripts/build-windows-x64-package.mjs` on Windows x64. The macOS production builder requires the release team’s `NIMI_MACOS_TEAM_ID`.

With the native package prepared, run these commands from the repository root on Apple Silicon. On Windows x64, use `windows-x86_64` for both target arguments.

```sh
pnpm --filter @nimiplatform/harness exec nimi-app build --target macos-aarch64 --production
pnpm --filter @nimiplatform/harness exec nimi-app pack --target macos-aarch64 --production
```

The build uses the workspace production builder declared in the Harness build profile. The pack step writes the local `.nimiapp` archive and its target metadata to `apps/harness/dist/nimi-app/`.

## Public release preflight

Run `pnpm exec nimi-app check --production` from the standalone publisher project with compatible published SDK, Kit and App Tools versions, its frozen lockfile, managed project files and a build command that works in that checkout. The workspace manifest here uses `workspace:*`, which the public dependency check rejects. Follow the publisher workflow for release and Registry submission. [Native release guide](../../app-tools/skills/nimi-app-lifecycle/references/release.md#native-desktop)

## Desktop tasks

The desktop composer copies selected or dropped files into the session workspace. Draft text, selected material references and the submit ID are saved together through account-scoped Kit storage. Successful Pi writes and edits open the original from the transcript. The workspace browser reads text and Markdown directly and can reveal other files in the OS. A recorded tool result refreshes an open preview, including changes made before the next model reply.

The desktop can queue a follow-up using the durable conversation inbox. Remote submissions keep their existing busy response. Session names are stored in the managed catalogue; the durable agent document owns the editable instructions used by the model. Opening a conversation with a pending run leaves the task waiting for the user's decision or explicit resume.

## Named session configurations

Home and Models & access share the configuration editor. The managed session catalogue stores a configuration reference. Each text step requests the observed revision, and each successful generation stores Runtime’s capture in its durable assistant message. Review session model applies an explicitly confirmed selection without resubmitting a task.

## Standard App framework

The Desktop/Electron reference generated by the locked App Tools package supplies the Host profile, Chrome Host, sandboxed preload and renderer bridge. The renderer reuses its `createDesktopNimiAppSession`, Session Provider, Access Gate, theme, NimiAppChrome, navigation controller and WorkbenchCore. ShiJing supplied a second integration reference for product navigation and the public ModelConfigAIConfigSurface. Models & access reads and edits this App’s AIConfig through the session client and offers Home account/App management entry points.

Harness owns the conversation view, fixed business IPC and durable databases. Framework navigation does not start a second agent loop. The original development registration, account namespace, conversation records and working directories are retained. `pnpm dev` verified the standard Chrome, back navigation, sidebar toggle, existing sessions, model picker and Home handoff. A new file-write decision survived stopping and reopening the same development registration, then approval completed the write and readback. Signed-out and cross-account journeys remain pending.

## First remote development slice (historical)

The Desktop Host registers the `ai.nimi.harness.sessions` Integration. In the development build, `session.list` serves up to 32 session references and titles. `session.submit` admits text under a conversation-scoped UUID and `session.inputStatus` reads its durable receipt. A duplicate with matching text uses its original receipt. Querying a receipt after Host restart does not start the model or tools. The installed 0.1.0 candidate exposes only the list operation. Home grants each consumer operation access. No file bytes or conversation content are included. The browser entry uses the App Tools Web Vite configuration and Kit Web session with the account and runtime access gate. For permitted operations it can submit new input, check the previous receipt, or explicitly retry that same input. Before dispatch it stores only the UUID and a digest of the text in the consumer’s managed storage for this target and session. The browser journey still requires a registered source.

The current workspace manifest declares canonical App ID `nimi.harness` with only the Electron desktop entry; the current official Registry has no Harness Web source, so an authenticated browser-to-PC round trip still requires separate Web source registration. The desktop and browser share no Electron capability or session database.

## Historical Web and Android development

The following commands and source identities belong to the earlier multi-platform project. The current workspace manifest declares the Electron desktop entry.

### Local Web to PC development

Use the two App Tools entry points with the local Realm. In the Harness directory run `pnpm dev` for the supervised PC app and, in a second terminal, `pnpm dev:web -- --realm local`. Set `NIMI_WEB_TLS_KEY` and `NIMI_WEB_TLS_CERT` in the untracked `.env.local` to a development certificate/key valid for 127.0.0.1 and trusted by the test browser. The Web entry is `https://127.0.0.1:4509/`, the local API is `http://127.0.0.1:3002`, and the sign-in UI is `http://localhost:3000`.

The local Realm needs the reviewed test client `ai.nimi.harness.web.dev` for App `ai.nimi.harness`, origin `https://127.0.0.1:4509`, callback `https://127.0.0.1:4509/`, role `app`, and App Access `integration.consume`. A non-production Realm can read its local admission document via `RUNTIME_CLIENT_REGISTRY_PATH`. In Home enable Developer Mode for the PC development registration, select the development provider, and confirm the browser source and the session operations being tested. The PC owns model configuration and file execution. Keep external data connectors ungranted for the attachment test.

### PC sessions from Web and Android

The shared remote view uses the public Kit session for each source. The PC remains the owner of the conversation, tools and files. Home grants each operation independently. A client can create a PC session without switching the desktop view, list sessions, send an input, check or stop it by receipt, read its final answer, or review and resolve a pending tool decision. A reply longer than 16,384 characters is shown as a preview. Tool arguments larger than 32 KiB must be reviewed on the PC.

Android development uses the App Tools mobile entry and Capacitor 8. The project compiles against Android SDK Platform 37.0 with AGP 9.1.1 and its Gradle 9.3.1 wrapper; Kit’s OkHttp Android dependency requires API 37. It targets API 36 and supports Android 12+ (API 31). For the local Realm, use the default debug package `ai.nimi.apps.harness.dev`, client `ai.nimi.harness.android.dev` and callback `ai.nimi.apps.harness.dev:/oauth/callback`. Build the APK and print the Gradle signing report on the Mac without selecting a device:

```sh
NIMI_ANDROID_BUILD_ONLY=1 pnpm dev:mobile -- --realm local
```

The debug output is `android/app/build/outputs/apk/debug/app-debug.apk`. Use the installed Android Build Tools' `apksigner verify --verbose --print-certs` on the APK and compare the SHA-256 **certificate** fingerprint with the debug variant of `:app:signingReport`. The local registry reviewer needs that public fingerprint and the exact package, client and callback. Build configuration alone does not admit a source.

For a local device run, allow USB debugging, reverse TCP 3000 and 3002 for sign-in and coordination, then run `pnpm dev:mobile -- --realm local`. Session and asset traffic uses the Runtime peer connection. Android 12+ and network reachability of the PC are required for this journey. The official Realm uses a separately reviewed HTTPS App Link and requires explicit `NIMI_ANDROID_CLIENT_ID` and `NIMI_ANDROID_REDIRECT_URI`.

For the hosted Web build, `pnpm build:web` accepts the App Tools release settings (`NIMI_WEB_ORIGIN`, `NIMI_WEB_REDIRECT_URI`, `NIMI_WEB_CLIENT_ID`, `NIMI_WEB_REALM_ENVIRONMENT_ID`, `NIMI_WEB_OFFICIAL_WEB_URL`). Serve `dist-web` with the root Pages `functions/` entry and configure its `NIMI_WEB_ORIGIN` and `NIMI_REALM_URL`. As in Zhiyu, only the allowed login and connection coordination routes are forwarded. Session control and file bytes travel over the authenticated Runtime connection. A local build does not register or deploy a source.

For an official Android debug run, match the registered package (optionally `NIMI_ANDROID_PACKAGE_NAME`) and signing certificate. If needed, use the same Gradle `nimiDebugKeystore` property as Zhiyu. Get the SHA-256 certificate fingerprint from the signed APK or its signing report. Verify the HTTPS callback host on the phone with `adb shell pm get-app-links <registered-package>` before testing sign-in.

With a Runtime that supports integration snapshot subscriptions, authorize `session.observeProgress` from the PC development provider to the local Web source. Its full snapshots coalesce intermediate changes; reconnect reads current state from the same PC session. The provider observes Pi durable commits, and cold observation opens no model or scheduler. Switching between the fixed and source Runtime on the same machine is a separate lifetime and primary-binding operation.
