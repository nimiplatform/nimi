# 四个闭合维度 (Four Closures)

“四个闭合”不仅仅是验收时要填写的表单字段，更是一种**核心的思考方式**。当感觉 AI 输出哪里不对、却又找不到具体哪一关没过时，就用它们来定位。

在 Nimi Coding 中，只有**全部四个维度**都显式达成，一个 Wave 才算真正闭合。“四过其三”绝不等于完成。

## 四个维度的核心拷问

| 维度 | 它所回答的核心问题 |
| --- | --- |
| 权威闭合 (Authority) | 这个功能面的真相源在哪里？它的内部逻辑自洽吗？ |
| 语义闭合 (Semantic) | 合同中的必填项、失败模式以及复杂场景，是否都已经显式定义了？ |
| 消费方闭合 (Consumer) | 消费这个接口的系统或读者，是否真的正确地使用了它？ |
| 抗漂移闭合 (Drift Resistance) | 下一个接手的开发者，是否很容易就会把这项设计退化回去？ |

## 权威闭合 (Authority Closure)

> 这个功能面的真相源在哪里？它的内部逻辑自洽吗？

权威闭合要求追问：在本次改动落地后，是否只存在**唯一一个**规范化的所有者（Canonical owner）？任何并行的真相面（如影子缓存、App 局部的便捷状态、双读路径）是被彻底消除了，还是被明确记录并准入了？

| 闭合（达成）的表现 | 未闭合（失败）的表现 |
| --- | --- |
| 规范化的所有者唯一 | 两个不同的面同时宣称自己拥有权威 |
| 不残留任何平行的真相源 | 某个非正式的缓存悄然变成了“事实权威” |
| 发生的修改行为皆经过显式准入 | 发生了隐秘的、绕过所有者准入的二次修改 |

**常见的权威闭合失败：** AI 随手补充了一个辅助函数，实质上却把另一个包本该管辖的行为重新实现了一遍，悄无声息地制造出了“影子真相”。

## 语义闭合 (Semantic Closure)

> 合同中的必填项、失败模式以及复杂场景，是否都已经显式定义了？

语义闭合要求追问：如果让两个不同的开发者来对接这份合同，他们写出的行为等价吗？MIME 类型、错误原因、重试策略和边缘场景行为，是已经在合同中钉死了，还是被“留给具体的实现代码自己决定”了？

| 闭合（达成）的表现 | 未闭合（失败）的表现 |
| --- | --- |
| 必填字段被严格指定 | 关键字段被遗漏或模糊处理 |
| 失败模式被清晰固化 | 只考虑了一切顺利时的“快乐路径 (Happy path)” |
| 复杂场景不被掩盖为隐性假设 | 遇到“边缘场景”就静默搁置不处理 |

**常见的语义闭合失败：** 典型的“只顾快乐路径”——AI 漂亮地实现了功能成功时的逻辑，却把异常捕获和失败处理全部留成了隐式。

## 消费方闭合 (Consumer Closure)

> 消费这个接口的系统或读者，是否真的正确地使用了它？那些“捷径”是否会悄悄变成主线？

消费方闭合要求追问：真正的消费方（App、文档读者、运维系统）是否真的通过你的工作解决问题了？有没有出现“合同落地做得很漂亮，但消费方那边依然处于损坏状态”的情况？

| 闭合（达成）的表现 | 未闭合（失败）的表现 |
| --- | --- |
| 正常的消费方在使用正确的接口对接 | 消费方实际上依然在用旧接口 |
| 临时的捷径无法悄悄转正 | 一个所谓的“临时捷径”变成了事实上的主流路径 |

**常见的消费方闭合失败：** 典型的“构建成功 / 消费方失败 (Build-pass / consumer-fail)”。此前我们修复公开文档的任务就是一个教科书般的例子：机器端的所有关口全部畅通放行，但真实的人类读者在阅读时拒绝买单，认为渲染出的文档就像“一堆干瘪的审计工件拼凑出的散文”。

## 抗漂移闭合 (Drift Resistance Closure)

> 下一个接手的开发者，是否很容易就会把这项设计退化回去？

抗漂移闭合要求追问：那些被明令禁止的捷径，被明确点名并封锁了吗？重开（Reopen）任务的条件写清楚了吗？防止系统功能退化的这堵墙，是靠结构化的机制强制守卫的，还是仅仅靠开发者之间的“口头默契”？

| 闭合（达成）的表现 | 未闭合（失败）的表现 |
| --- | --- |
| 禁用的捷径被显式列出并封禁 | 捷径未被点名，后来者可能会重新“发明”它 |
| 后来者无法轻易地绕过准入去削弱设计 | 设计的边界脆弱，可以被随意修改而不触发警报 |

**常见的抗漂移失败：** 任务在今天看来闭合得很完美，但没有任何机制来阻止同样的偷懒做法在下个季度（当大家都忘了这回事的时候）卷土重来。

## 为什么四个维度必须独立看待？

**“四过其三”是 AI 开发中最具迷惑性的伪闭合形态。** 每一种“过三差一”的组合，都会催生出一种典型的工程病态：

| 权威 | 语义 | 消费方 | 抗漂移 | 结果 |
| --- | --- | --- | --- | --- |
| ✓ | ✓ | ✓ | ✗ | 今天跑得好好的，半年之后烂在锅里 |
| ✓ | ✓ | ✗ | ✓ | 技术上绝对正确，但实际完全没法用 |
| ✓ | ✗ | ✓ | ✓ | 用户体验绝佳，但接口定义一塌糊涂 |
| ✗ | ✓ | ✓ | ✓ | 暗中埋下了平行的影子权威 |

因此，方法论要求**全部四个维度都必须被显式达成**。只要缺失任何一个维度，这就是一起结构上的违规（Schema violation），而不是什么无关痛痒的建议。

## 场景案例：用四个闭合框架来走查一个 Wave

假设你是 Manager，正在评审一个 Wave 的收尾（Closeout）结果。执行者（Worker）说已经干完了，你拿出四个闭合维度开始走查：

1. **权威闭合**：事实真相依然存放在 `.nimi/spec/**` 吗？有没有弄出什么影子路径？归属权足够清晰吗？
2. **语义闭合**：核心规则依然锁住了必填项、失败模式和数据结构吗？复杂的边缘情况都被显式处理了吗？
3. **消费方闭合**：真正的用户（App 或读者）觉得问题解决了吗？实际跑一次代码、读一遍渲染后的文字、调一次 API 试试看。
4. **抗漂移闭合**：禁用捷径目录更新了吗？重开条件写清楚了吗？未来一次匆忙的 Hotfix 有没有可能把错误的模式又带回来？

只要有一项（比如消费方体验）没过，那么这个 Wave 就是**未闭合**的。你必须将其打回修改，或者再准入一个新的 Wave，专门用来填补消费方层面的缺口。

## 场景案例：一次真实的“四过其三”

之前的公开文档修复任务在机器审计阶段是这样闭合的：权威闭合（Spec 没跑偏），语义闭合（声明和 Spec 严丝合缝），抗漂移闭合（禁用特定主张的防线还在）。但消费方这一栏**失败了**——人类用户拒绝了这篇毫无生气的文档。

在这套方法论下，正确的处理方式是：把 Topic 维持在 `Pending` 状态（不要去标记为 `Closed`）；再准入一个新的 Wave 去专攻消费方体验。**千万不要回头去篡改那个已经在机器层面闭合的 Wave 的历史记录。**

这就是四个闭合框架的价值所在：如果没有它，那么仅仅依据“编译通过”，那篇烂文档就已经蒙混过关了。
