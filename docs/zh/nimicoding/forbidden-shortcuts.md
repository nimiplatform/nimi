# 禁用捷径目录 (Forbidden Shortcuts)

Nimi Coding 提供了一份**由包维护的具名反模式目录**。目录里的每一个“捷径”，都是一种被方法论严令禁止的具体失败形态；并且，每一个捷径都对应一个唯一的 Key，以便在工作包（Packet）中直接被引用。

这是在工程决策上极具特色的一点：虽然这个目录是开放的，Topic 能够声明自己特有的扩展规则，但**所有被拒绝的模式都必须有明确定名的 Key**。在这里，不存在名为“诸如此类的烂代码”这种含糊不清的筐。

## 目录概览

| Key | 所禁止的行为 |
| --- | --- |
| `mvp_subset_contract` | 禁止把权威合同随意切割为临时的最小功能子集 —— 完整设计必须先行。 |
| `legacy_alias` | 禁止通过软别名（Soft alias）给过时的语义强行续命 —— 旧逻辑必须果断硬切，不能软着陆。 |
| `compat_shim` | 禁止用临时的兼容性代码（Shim）去遮掩归属权变更（Owner-cut）造成的缺口。 |
| `dual_read` | 禁止在未经显式准入的情况下，偷偷保留并行的读真相路径。 |
| `dual_write` | 禁止在未经显式准入的情况下，偷偷保留并行的写真相路径。 |
| `placeholder_success` | 禁止在缺失核心真相时，随便扔个占位符出来假装闭合成功。 |
| `happy_path_only_closure` | 禁止仅仅跑通了“快乐路径（Happy path）”就敢宣布闭合成功。 |
| `time_phased_layering` | 禁止用纯粹的时间分层（v1 / v2 / v3）来取代语义分层（Core / Extended / Custom） —— 本方法论认的是业务本体，而非时间线。 |
| `app_local_shadow_truth` | 禁止让 App 内局部的为了图方便而产生的小状态，演变成为隐藏的规范权威真相。 |
| `silent_owner_cut_reopen` | 禁止在执行下游任务的 Wave 中，悄悄篡改上游专属的权威域真相。 |

内置在这份目录里的 10 种模式是整座大厦的基石。各个 Topic 固然可以声明它自己的扩充规则，但要么使用内置的 Key，要么使用自己明确声明的扩展 Key —— 绝对不允许使用无格式的散文来敷衍。

## 为什么要建一个目录，而不是直接写“注意事项”？

如果仅仅是留一段自由发挥的文字让大家“避免干这些事”，那在实操中是极难监督的。评审者们哪怕在精神上达成了共识，也会在“这行代码到底算不算犯规”上吵得不可开交。更何况，机器审计程序根本无法对长篇大论进行机械化校验。

把“绝对不准做的事”整理成目录，并赋予确定的 Key，就能化模糊为利器：工作包（Packet）明确宣誓绝不触碰哪些 Key；审计员（Auditor）拿着这份宣誓逐一对照；在收尾（Closeout）阶段，抗漂移维度也会最后把关，确认这些禁忌依然被严密防范着。

## 反模式详解

### `mvp_subset_contract` (最小子集合同)

准入了一份只具备最小功能集的合同，把剩下的部分推脱说“我们以后再加”。方法论禁止这种做法，因为：
- 所谓的“以后”，本质上就是 `time_phased_layering`（时间版本分层）。
- 一个不完整的子集合同，会把那些没解决的顾虑变成隐性默认值。
- 下游消费方一依赖了这个子集，未来你再想扩充它，就会变成披着“完善功能”外衣的破坏性修改。

**正确做法**：必须一次性设计出完整的合同全貌；采用基于业务本体的分层准入（Core / Extended / Custom），坚决弃用按时间切分的版本分层（v1 / v2 / v3）。

### `legacy_alias` (旧别名残留)

通过设置软别名的方式，让已经过时的语义苟延残喘。方法论禁止这种做法，因为：
- 这个别名本身就是制造出来的一个平行真相。
- 它会悄无声息地施加兼容性负担。
- 它会让未来的重构变成一场噩梦，而不是越来越轻松。

**正确做法**：一刀切（Hard cut）。你要么承认它依然是合法的权威真相，要么就彻底斩草除根。那些标榜着“为了迁移而暂时存在”的别名，最后无一例外都会变成永久的伤疤。

### `compat_shim` (兼容垫片)

用一层临时的兼容性垫片（Shim）把归属权变更留下的坑给捂住。这其实就是发生在所有权更迭上的 `legacy_alias`，同样严厉禁止。

### `dual_read` / `dual_write` (双读写路径)

在未获显式准入的情况下，任由平行的双套读路径或双套写路径同时存在。被禁的理由：
- 这两条路径势必会发生漂移。
- 依赖其中一条路径的 App 根本不知道另一条发生了什么。
- 所谓的“正在从一条路径向另一条迁移”，极易沦为一种永久状态。

**正确做法**：光明正大地把“双套真相并存”作为一份过渡期合同予以准入，并且必须清楚标注出废弃的时间表和验证闭合的标准。

### `placeholder_success` (占位式成功)

明明类型合同在校验上翻车了，却套上一个 fallback，扔出个“不知道什么鬼东西”来假装成功，拒不安全报错（Fail-closed）。被禁的理由：
- 下游代码压根接收不到任何事态崩坏的信号。
- 这个随便扔出来的“什么鬼东西”居然变成了事实上的接口。
- 机器审计完全被蒙在鼓里，查不出错。

**正确做法**：老老实实报错（Fail-closed），并附上类型化的问题定位。我们只允许在网络传输或授权鉴权层面使用运行时重试（Run-time recovery），绝不许用在拯救业务合同逻辑上。

### `happy_path_only_closure` (仅凭快乐路径就闭合)

光把一切顺利时的流程跑通，就迫不及待地高呼闭合，完全不去理会隐形的失败模式。这在“语义闭合”维度上严重违规。

**正确做法**：在敢拍胸脯宣告语义闭合前，必须把所有可能的失败模式全部显式钉死。

### `time_phased_layering` (按时间版本分层)

完全按照时间顺序（v1 → v2 → v3）来为代码分层，而不是按照抽象本体（基础 / 扩展 / 自定义）来分层。被禁的理由：
- 以时间为尺度的分层，只会制造无休止的“旧版废弃、新版上位”的动荡。
- 每出一个“下个版本”，其实都是在搞一次变相的 `legacy_alias` 软迁移。
- 按本体逻辑进行的分层，在语义上坚如磐石；按时间分层的，则是一盘散沙。

**正确做法**：按它在业务模型里的抽象含义（例如 Core、Extended 等）来分层，而不是按“它是哪天被加进来的”来分层。

### `app_local_shadow_truth` (App 内的影子真相)

App 内部为了使用方便而暂存的临时状态，渐渐越俎代庖成了隐藏的规范权威真相。被禁的理由：
- 很快，该 App 本地的状态就会和真正的规范发生分歧。
- 其它 App 的处理逻辑必然与它产生冲撞。
- 机器审计再也无法溯源。

**正确做法**：明确认定 App 的状态就是朝生暮死的局部缓存；任何希望以“真相”之名长期留存的信息，必须乖乖交还给对应的归属域（Owner domain）。

### `silent_owner_cut_reopen` (悄无声息地重开权威域真相)

在处理下游任务的执行 Wave 中，夹带私货，偷偷修改上游的归属域真相。被禁的理由：
- 归属域状态的改变，必须走它专有的准入申请通道。
- 把这种敏感修改混搭到下游的执行流程里，会把权威漂移掩盖得严严实实。
- 审计追溯链条（Lineage）将彻底变得无源可寻。

**正确做法**：先老老实实去为归属域的修改走一套独立的 Wave 准入；做完之后，再让下游任务顺着更新完毕的新真相继续往下跑。

## Packet 是如何声明禁用捷径的？

工作包（Packet）内的 `forbidden_shortcuts` 字段，负责列出被这趟任务坚决抵制的所有 Key：

```yaml
forbidden_shortcuts:
  - mvp_subset_contract
  - legacy_alias
  - compat_shim
  - dual_read
  - dual_write
  - placeholder_success
  - happy_path_only_closure
  - time_phased_layering
  - app_local_shadow_truth
  - silent_owner_cut_reopen
```

同时，一个 Topic 可以声明它自己专属的本地扩展：

```yaml
forbidden_shortcuts:
  # 包内置的 keys
  - mvp_subset_contract
  - legacy_alias
  # 某 Topic 自定义的扩展
  - sidebar_links_to_unwritten_pages
```

再次强调，Topic 的本地扩展必须被显式**声明（declared）**并赋予具体的名称，严禁随便写一段自由格式的散文就糊弄过去。

## 场景案例：一次审计查出了违规操作

你手上的一个 Wave 正在接受审计。审计结果发现代码里藏了一招 `legacy_alias`：某个老路由居然被留下来了，美其名曰“仅仅是为了帮助过渡迁移”。

| 步骤 | 发生了什么 |
| --- | --- |
| 审计员发现问题 | 该实现手法命中了目录中的 `legacy_alias` 反模式 |
| 下达审计结论 | `NEEDS_REVISION`（需修订）；如果性质极度恶劣甚至是 `FAIL` |
| 执行者（Worker）补救 | 要么乖乖把老别名删个干净，要么堂堂正正把它确立为一份过渡期的明文合同 |
| 重新审计 | 核查是否已彻底整改 |

正是这个具有高度威慑力的目录，让每一次违规行为变得**名正言顺、类型明晰**。这种模式到底能不能用？有目录在，绝无扯皮的余地。
