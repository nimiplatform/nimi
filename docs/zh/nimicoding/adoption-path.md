# 采纳路径

谁会采纳 Nimi Coding、为什么？这页按真实使用场景说明它解决什么问题。

## 适合谁

| 使用者 | 直接收益 |
| --- | --- |
| 重度依赖 AI 的独立开发者或 solo 创业者 | 没有团队，也能保留接近团队审查的结构 |
| 正在引入 AI 的小团队（2-5 人工程师） | 不靠增加人手，也能扩大审查覆盖 |
| 接收 AI 生成 PR 的开源维护者 | 看到贡献者被什么边界约束、凭什么声称完成 |
| 有 AI 开发合规压力的工程组织 | 留下可审计、可交接的工作记录 |
| 研究 AI 工程实践的人 | 得到结构化、可比较的方法论样本 |

## 来自 Nimi 自身的证据

Nimi Coding 最有说服力的证据不是跑分，而是 Nimi 自己就在使用这套方法。

在 Nimi 仓库里，Nimi Coding 用来：

- 重建并校验 `.nimi/spec/**` 这棵规范权威树；
- 用 topic 组织设计、审计和修复，而不是让 AI 在一段长聊天里自由发挥；
- 把长时间审计拆成 sweep audit chunk，并为每个 chunk 记录证据；
- 把 audit finding 转成 sweep design 工作集，再进一步变成候选 wave；
- 让横跨 runtime、SDK、desktop、docs、Nimi Coding 自身的修复仍然能被追踪和复审。

这并不等于说方法论已经被证明适用于所有项目。它真正有价值的地方在于可证伪：如果工件漂移了、topic 没证据就闭合了、spec audit 断了、用户没有接受却被标成完成，这些失败都会暴露在同一套机制里。

## 重度依赖 AI 的独立开发者

这是最难的场景。一个人想做一个有野心的系统，必须借助 AI 提高速度，但又没有团队成员帮忙做第二轮判断。

常见问题：

- 自己审自己不可靠。
- 测试能抓行为 bug，却很难抓权威漂移。
- AI 产出的东西看起来合理，但在单一会话里很容易逃过复查。

Nimi Coding 的作用：

- Auditor 可以交给另一个 AI session 或另一个厂商，制造结构上的第二视角。
- 四闭合框架让「做完了吗」用证据回答，而不是靠感觉。
- 禁用捷径目录提前命名那些独立开发者未必已经见过的失败模式。

这正是 Nimi 自己的使用场景。Nimi 由一个重度使用 AI 的 solo 创业者推进，Nimi Coding 的作用是让这些工作在聊天上下文消失之后仍然可复查。

## 正在引入 AI 的小团队

小团队会很早遇到 AI 的失败模式，因为 AI 会放大产出速度，但不会自动放大审查能力。

常见问题：

- AI 让 PR 变多，审查能力却没有线性增长。
- 权威漂移通常不是单个 PR 里一眼可见的问题，而是在几周里慢慢累积。
- 团队忙起来以后，「看起来可以」容易变成默认通过。

Nimi Coding 的作用：

- 正常 PR 审查继续保留，Nimi Coding 额外提供独立的审计循环。
- 禁用捷径目录帮审查者捕捉重复出现的 AI 失败模式。
- Topic / wave 让团队一次聚焦一条主要迭代线，避免大任务变成散乱补丁。

对小团队来说，核心价值是：不用靠增加人手，也能获得更稳定的审查结构。

## 接收 AI 生成 PR 的开源维护者

维护者真正需要的不是一句「这是 AI 帮我写的」，而是能判断这次贡献有没有边界、有没有证据、有没有跟项目规范冲突。

常见问题：

- AI 生成的 PR 可以很精致，却仍然偏离项目 spec。
- 维护者很难从 PR 描述里分清哪些推理有证据，哪些只是模型补出来的。
- 当贡献者是模型或模型驱动的人类时，单纯相信贡献者很难扩展。

Nimi Coding 的作用：

- 冻结 packet 写清楚贡献者被哪些读写边界约束。
- 审计记录让维护者直接看证据，不必从 PR 描述里反推发生了什么。
- 四闭合记录让维护者在合并前判断：权威、语义、消费方、抗漂移是否都成立。

对开源维护者来说，价值是：AI 贡献不再只是代码 diff，而是带有结构证据的贡献。

## 有 AI 开发合规压力的工程组织

更大的组织需要回答的不只是「代码能不能跑」，还包括 AI 参与了什么、被什么约束、谁接受了结果、后续团队能不能复查。

常见问题：

- 事后很难回答「这次是不是 AI 辅助开发」。
- 从 PR 很难看出 AI 当时被哪些边界约束。
- 审计、安全、合规团队不能依赖自由聊天记录来证明治理过程。

Nimi Coding 的作用：

- `.nimi/topics/**` 留下结构化工作记录。
- `topic.yaml` 记录生命周期状态。
- 四闭合记录提供结构化接受标准。
- 审计记录把建议、裁定、接受和执行串起来。

对工程组织来说，价值是：AI 辅助工作可以被审计、被交接、被复查。

## 研究 AI 工程实践的人

研究者需要的不是零散故事，而是能跨团队比较的结构化材料。

常见问题：

- 许多 AI 编程证据只存在聊天记录里，很快消失。
- 「某种 AI 失败模式到底长什么样」很难只靠轶事回答。
- 方法不成型时，不同团队之间很难复现和比较。

Nimi Coding 的作用：

- 让不同团队能产出形状相近的 topic、packet、审计和闭合记录。
- 用伪闭合分类命名反复出现的失败形态。
- 把 AI 工程实践变成可观察、可比较的材料。

对研究者来说，价值是：AI 工程不再只是一串聊天记录，而是可分析的方法论样本。

## 什么时候**不**采纳

方法学**对它的适用范围显式**：

| 情况 | 用 Nimi Coding？ |
| --- | --- |
| 高风险或承载权威工作 | 是 |
| 复杂 remediation | 是 |
| 多 wave 迭代 | 是 |
| 跨模块 refactor | 是 |
| 极小本地修 | 否（开销超价值） |
| 一次性脚本 | 否 |
| 一次性 prototype | 否 |

把这套方法强加到小改动上，只会增加成本，不会增加闭合价值。小改动默认走正常工程卫生，不需要 topic。

## 阅读场景：Solo 创业者第一次采纳 Nimi Coding

某个独立开发者正在用 AI 辅助建设一个有野心的系统。

1. **取得包。** 见 [安装](/zh/nimicoding/installation)。
2. **跑 `nimicoding start`。** Bootstrap 准入。
3. **重建 spec。** 用 `nimicoding handoff --skill spec_reconstruction --json` 把任务交给已准入的宿主。
4. **为下一次高风险改动创建 topic。** 写清目标、准入 wave、冻结 packet。
5. **安排审计。** 用不同 AI session 执行 auditor 角色。
6. **闭合 wave。** 四个闭合维度都成立才算完成。
7. **继续。** 后续高风险改动走同样纪律。

六个月后，这位开发者拥有每次实质改动的结构化证据。权威漂移可以被发现，主会话里漏掉的问题也有机会被审计循环抓住。

## 阅读场景：维护者用 Nimi Coding 审查 PR

某个中等流量开源项目的维护者决定为 AI 生成的 PR 引入 Nimi Coding。

1. **把包加为开发依赖。** 在项目装 Nimi Coding。
2. **在主分支初始化 `.nimi/`。** 方法学 + spec 结构变成项目一部分。
3. **更新贡献指南。** AI 生成的 PR 必须带 topic / wave / packet 工件。
4. **维护者读工件。** 冻结 packet、审计记录、闭合记录一起进入 PR 审查。
5. **闭合后再合并。** Wave 闭合，PR 才能合并。

这项规则主要约束 AI 贡献；普通人类贡献在常规情况下不受影响。
