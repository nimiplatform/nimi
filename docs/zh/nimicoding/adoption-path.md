# 采纳路径 (Adoption Path)

谁会采纳 Nimi Coding？为什么采纳？本页将根据真实的工程场景，详细说明它为不同类型的开发者和团队所解决的核心痛点。

## 核心受众与直接收益

| 目标受众 | 核心收益 |
| --- | --- |
| **重度使用 AI 的独立创业者** | 无需组建团队，即可获得接近专业团队的评审纪律。 |
| **正在引入 AI 的小规模团队** | 无需增加人手，即可实现更高质量的评审覆盖率。 |
| **接收 AI 生成 PR 的开源维护者** | 明确贡献者的变更边界，凭证据而非直觉进行合并。 |
| **有合规压力的工程组织** | 留下完整、可审计、可交接的 AI 开发记录。 |
| **AI 工程实践的研究者** | 获得结构化、可观察、具备可比性的方法论样本。 |

---

## 实战证言：Nimi 自身的实践

Nimi Coding 最有力的证据并非实验室数据，而是 Nimi 平台本身就在重度使用它。

在 Nimi 的核心仓库中，我们使用 Nimi Coding 来：
- 重建并校验 `.nimi/spec/**` 这一“唯一真相树”；
- 利用 Topic 组织架构设计、审计与修复，而非让 AI 在发散的聊天中盲目修改；
- 将漫长审计拆成 sweep audit chunk，并为每个 chunk 记录证据；
- 将 audit finding 转成 sweep design 工作集，再进一步变成候选 Wave；
- 确保跨越 Runtime、SDK、Desktop、文档和 Nimi Coding 自身的复杂修复工作依然具备可追溯性。

**具备可证伪性 (Falsifiability)**：这套机制最珍贵的地方在于，一旦发生设计漂移、未授权闭合或用户接受度缺失，所有的失败都会显式地暴露在治理工件中，无法掩盖。

---

## 场景一：重度依赖 AI 的独立创业者 (Solo Founder)

这是最具挑战性的场景。一个人想要构建一套野心勃勃的系统，必须借助 AI 的极速产出，但又缺乏团队成员来进行“第二轮审视”。

- **痛点**：自己审阅自己的代码极不可靠；AI 生成的“看似合理”的产物很容易逃过复核。
- **Nimi Coding 的价值**：
    - **异构审计**：将审计角色路由至另一个 AI 厂商或另一段独立的会话，制造结构化的第二视角。
    - **证据驱动**：用四个闭合维度的刚性证据回答“做完了吗”，彻底告别“凭感觉开发”。

---

## 场景二：正在引入 AI 的小团队 (2-5 人)

小团队往往最先遭受到 AI 失败模式的冲击。因为 AI 极大地放大了产出速度，但团队的评审能力并不会随之线性增长。

- **痛点**：PR 数量激增，评审流于形式；权威漂移在数周的琐碎改动中悄然累积。
- **Nimi Coding 的价值**：
    - **评审冗余**：在常规 CR 之外，提供一个独立的审计循环，且无需额外增加人力。
    - **专注主线**：通过 Topic/Wave 纪律，强迫团队一次只聚焦一条主要迭代线，防止任务碎裂化。

---

## 场景三：接收 AI 生成 PR 的开源维护者

维护者需要的不是一句“这是 AI 写的”，而是能确信这次贡献是否有边界、是否有据可查、是否破坏了项目规范。

- **痛点**：AI PR 看起来很精致，但可能隐含了与 Spec 冲突的逻辑；维护者很难分辨哪些是基于证据的推理，哪些是模型的幻觉。
- **Nimi Coding 的价值**：
    - **刚性边界**：通过冻结 Packet 明确贡献者被限制在哪些读写边界内。
    - **结构化合并**：在合并 PR 前，维护者只需核验四闭合记录。**AI 贡献不再只是代码 Diff，而是带有结构化证据的文明贡献。**

---

## 场景四：有 AI 开发合规压力的工程组织

更大的组织需要回答的不只是“代码能不能跑”，还包括 AI 参与了什么、被什么边界约束、谁接受了结果、后续团队能不能复查。

- **痛点**：PR 很难还原 AI 当时被哪些边界约束，自由聊天记录也不能作为稳定治理证据。
- **Nimi Coding 的价值**：
    - **结构化记录**：`.nimi/topics/**`、`topic.yaml`、审计记录和 closeout 记录把过程留在仓库里。
    - **可交接**：后续团队可以复查每次 AI 辅助工作的范围、裁定与接受度，而不是依赖某段已经消失的聊天上下文。

## 场景五：AI 工程实践研究者

研究者需要的不是零散故事，而是能跨团队比较的结构化材料。

- **痛点**：许多 AI 编程证据只存在聊天记录里，失败模式难以复现和比较。
- **Nimi Coding 的价值**：
    - **统一形状**：不同团队能产出形状相近的 Topic、Packet、审计和闭合记录。
    - **可观察样本**：伪闭合分类和禁用捷径目录把失败形态命名，便于分析。

## 设计层面的适用边界

方法论明确声明了它的**适用范围**，不建议盲目扩大化：

| 任务类型 | 是否建议使用 Nimi Coding？ |
| --- | --- |
| 高风险变更或架构权威变更 | **建议使用** |
| 复杂的架构修复 (Remediation) | **建议使用** |
| 多 Wave 协同的长周期迭代 | **建议使用** |
| 跨模块重构 | **建议使用** |
| 极小的本地 Bug 修复 | 不建议（管理成本超过价值） |
| 一次性脚本或临时原型 | 不建议 |

**核心姿态**：对于微小的改动，我们建议遵循常规的工程卫生习惯即可，无需引入繁重的 Topic 纪律。
