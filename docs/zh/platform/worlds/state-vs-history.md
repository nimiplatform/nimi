# 状态与历史

> 状态：当前规范生效中。世界状态（`R-WSTATE-*`）与世界历史（`R-WHIST-*`）是 Realm 提供的两个核心数据表面，定位互补、职责分明。

一个世界在 Realm 中持久化两份核心记录：**状态**（State，即当前此刻的世界事实）与**历史**（History，即已经发生的事实序列）。两者相互独立，不可互相替代，平台通过严格的规则判定每一次变更所影响的数据表面。

## 什么是状态 (State)

| 属性 | 规范定义 |
| --- | --- |
| 权威所有者 | Realm World State (`R-WSTATE-*`) |
| 核心目标 | 维护世界共享的当前最新状态 |
| 作用范围 | 仅限持久化共享作用域：`WORLD`、`ENTITY`、`RELATION` |
| 变更方式 | 显式提交变更信封 (Commit Envelope) |
| 故事/本地控制变量 | 不在 Realm 内维护，由 App 本地私有管理 |

状态反映的是当前时刻公认的共享事实：某个角色当前身处的位置、一段关系当前的发展阶段、一个实体当前拥有的属性。状态必须通过显式的变更信封提交才能更新。

## 什么是历史 (History)

| 属性 | 规范定义 |
| --- | --- |
| 权威所有者 | Realm World History (`R-WHIST-*`) |
| 核心目标 | 维护权威的事实变迁记录与审计溯源 |
| 写入方式 | 显式追加 (Append-Only) |
| 故事追踪/原始推理日志/应用私有存档 | 不写入 Realm 历史表面 |
| 单条记录溯源字段 | `appId`、`sessionId`、`actorRefs`、`reason`、`evidenceRefs` 及关联的状态/权威锚点 |
| 变更规则 | 仅允许追加；纠错通过标明“取代”或“失效”的新记录实现，禁止物理硬删除 |

历史记录的是已经发生并获得确认的权威事实：在哪个回合提交了哪笔变更，由哪个 App 在哪种运行模式下写入。它不是模型逐字逐句的流式输出日志，而是经过平台验证与认可的正式事件序列。

## 由 `effectClass` 决定更新表面

每个变更信封必须声明其变更影响类别 `effectClass`：

| `effectClass` | 状态写入 (State Write) | 历史追加 (History Append) |
| --- | --- | --- |
| `NONE` | 否 | 否 |
| `STATE_ONLY` | 是 | 否 |
| `STATE_AND_HISTORY` | 是 | 是 |

客户端不可自定义新的变更类别，枚举值受协议强约束。

## 运行模式授权

对世界状态的写入需要经过显式的 App 权限校验，依据 `(appId, schemaId, schemaVersion, effectClass) -> runMode` 授权矩阵进行核对，并配合严格的 Schema 模式校验。缺少必要 Schema 字段、未注册的 Scope、无法验证的来源凭据或未经授权的运行模式，均会导致提交直接被拒。

历史记录追加的约束规则：

| 规则 | 约束条件 |
| --- | --- |
| `REPLAY` 运行模式严禁追加共享世界历史 | `R-WHIST-004` |
| 仅限矩阵显式授权 `CANON_MUTATION` 权限的操作追加历史 | `R-WHIST-004` |
| App 私有叙事日志与本地存档 | 由 App 自身独立持久化，不得混入 Realm 历史 (`R-WHIST-006`) |

## 为什么区分两个独立表面

如果用**状态替代历史**：
- “这个实体之前在什么位置？”将无从追溯与解答。
- 审计、回放、复盘以及确定性重构将无法实现。
- 依靠静默覆盖来更新数据，会破坏可追溯性与数据信噪比。

如果用**历史替代状态**：
- 每次查询“这个实体现在在哪”，都必须从庞大的历史事件流中从头回溯重放。
- App 的每次读取都需要承受不可预测的时间与计算开销。
- 高并发追加操作竞态时，“当前时刻”的状态定义将变得模糊不定。

两套独立表面，服务于统一的数据模型。每次操作通过 `effectClass` 显式声明其影响范围。

## 典型场景：`STATE_ONLY` 瞬态更新

App 提交一次无历史归档意义的瞬态世界状态变更：

1. **提交变更信封**：App 提交请求，声明 `effectClass: STATE_ONLY`。
2. **Realm 校验**：Schema 结构、来源凭据以及运行模式授权均校验通过。
3. **状态生效**：世界的当前状态即时反映最新数据。
4. **历史保持不变**：没有新增历史记录；该变更有状态效力，但不沉淀为长期历史。

## 典型场景：`STATE_AND_HISTORY` 规范变更

App 提交一次具有权威里程碑意义的世界变更：

1. **提交变更信封**：声明 `effectClass: STATE_AND_HISTORY`。
2. **Realm 校验**：通过基础检查，并进一步确认当前运行模式具备历史追加授权 (`CANON_MUTATION`)。
3. **状态生效**：世界当前状态完成更新。
4. **历史追加**：生成带有完整溯源元数据的新历史条目并完成持久化。
5. **后续引用**：后续的状态回放或数据校验均可可靠引用该记录。

## 典型场景：历史记录纠错与修正

一条较早的历史记录被发现存在事实偏差需要修正：

1. **禁止物理硬删除**：原历史记录保持原样保留；纠错通过生成一条标明“取代”或“使失效”的新事件来表达。
2. **追加修正事件**：新事件明确关联并引用原记录 ID，说明修正原因与取代逻辑。
3. **严格追加不变性**：审计方既能查看最初记录，也能查看纠错过程，历史追溯链保持完整。

仅追加 (Append-Only) 的不变性保证了 Realm 历史作为长期可信审计表面的可靠性。

## 典型场景：回放 (Replay) 消费者尝试写入历史

一个用于重现过程的 Replay 消费者在回放期间试图向历史追加数据：

1. **回放执行**：系统在 `REPLAY` 模式下重新计算推导状态变化。
2. **拦截历史追加**：根据 `R-WHIST-004` 规则，`REPLAY` 运行模式严禁向共享历史追加新行。
3. **状态写入受控继续**：若授权矩阵允许该模式更新局部状态，状态写入正常完成；历史数据则被严格隔离，不产生重复污染。
4. **审计一致性**：明确标识为重放路径，Realm 共享历史不受干扰。

## 典型场景：App 自有叙事日志存档

某个剧情 App 需要记录每位玩家独立的故事对话流与叙事上下文：

1. **不属于 Realm 历史范畴**：Realm 历史仅用于记录平台规范公认的事实。
2. **App 自行管理**：App 将丰富的叙事对话保存在自有的数据存储中 (`R-WHIST-006`)。
3. **不得冒充 Realm 历史**：App 不得将私有叙事存档伪装为 Realm 规范的世界历史发布。

## 关键设计红线

- 状态与历史界限清晰，不得隐式混淆。
- `effectClass` 采用封闭枚举，不支持私有扩展。
- Realm 不支持任何绕过显式变更信封的隐式旁路写入。
- `REPLAY` 运行模式严禁静默追加历史记录。
- App 私有存档绝不作为 Realm 规范权威状态。
- 历史记录严禁静默物理硬删除。

## 职责边界速查

| 关注点 | 权威所有者 |
| --- | --- |
| 共享当前最新状态 | Realm (`R-WSTATE-*`) |
| 规范历史事实与审计记录 | Realm (`R-WHIST-*`) |
| 变更信封提交权威 | Realm (`R-WSTATE-002`) |
| 运行模式授权矩阵 | Realm (`R-WSTATE-005`) |
| `effectClass` 封闭枚举 | Realm (`R-WSTATE-004`) |
